## 1. 这是什么

YotCode 是一个在终端里运行的 AI 编程助手。它和 Claude Code 的工作方式类似：

- 你用自然语言描述任务；
- 模型读取文件、搜索代码、执行命令、修改文件；
- 每一步工具调用都会显示在对话时间线上；
- 写文件、执行命令前会按权限规则询问你；
- 对话会保存为 JSONL，可以随时恢复；
- 支持项目记忆、斜杠命令、子代理、Hooks、MCP 和无头脚本模式。

它不依赖任何厂商 SDK，只使用三个库：

| 库 | 作用 |
|---|---|
| `textual` | 终端 TUI |
| `rich` | Markdown、diff、表格、颜色 |
| `httpx` | 流式 HTTP 请求 |

## 2. 安装

### 2.1 环境要求

- Python **3.10 或更高版本**
- Windows 10/11、macOS 或 Linux
- 一个支持工具调用（tool use / function calling）的模型

检查 Python：

```bat
python --version
```

### 2.2 Windows 一键安装

在项目根目录双击或运行：

```bat
setup.cmd
```

它会：

1. 创建 `.venv` 虚拟环境；
2. 升级 pip；
3. 安装 `textual`、`rich`、`httpx`、`pytest` 等依赖；
4. 以可编辑模式安装 `yot` 命令。

默认使用清华 PyPI 镜像。如果想改用官方源：

```bat
set YOTCODE_PIP_INDEX=https://pypi.org/simple
setup.cmd
```

安装完成后运行：

```bat
run.cmd
```

`run.cmd` 会自动切换到 UTF-8 代码页，并把参数原样传给 CLI。

### 2.3 macOS / Linux 手动安装

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -e .
yot
```

也可以只安装运行依赖：

```bash
pip install textual rich httpx
python -m yotcode
```

### 2.4 不配置 API Key 也能体验

内置离线 Mock 模型，适合先看界面和工具流程：

```bat
run.cmd --mock
```

或：

```bash
yot --mock
```

Mock 模型不会访问网络，但会演示流式输出、工具调用、diff、待办列表等。

### 2.5 首次启动会看到什么

- 顶部：品牌、当前目录、Git 分支、模型胶囊、`^P` 命令面板提示；
- 中间：对话时间线；
- 底部：输入框、提示行、状态栏。

如果没有任何 Key，会显示一段设置提示，并给出 `--mock` 的用法。

### 2.6 从 claudepy 改名过来的用户

这个项目以前叫 **claudepy**，现在叫 **YotCode**。老用户不用做任何事：

| | 以前 | 现在 |
|---|---|---|
| 命令 | `claudepy` / `ccpy` | **`yot`**（老命令仍然可用） |
| Python 包 | `claudepy/` | `yotcode/` |
| 项目配置目录 | `.claudepy/` | **`.yotcode/`** |
| 用户配置目录 | `~/.claudepy/` | `~/.yotcode/` |

**第一次启动时会自动迁移**：老目录整个改名成新目录，里面的 `settings.json`、
`commands/`、`agents/`、`skills/`、会话记录、检查点全都原样带过去。
新目录如果已经存在，则**不会覆盖**你已有的东西。

环境变量加了 `YOTCODE_` 前缀，旧的 `CCPY_*` / `CLAUDEPY_*` 依然认：

| 新名字 | 旧名字（仍可用） |
|---|---|
| `YOTCODE_HOME` | `CCPY_HOME` / `CLAUDEPY_HOME` |
| `YOTCODE_FONT_SIZE` | `CLAUDEPY_FONT_SIZE` |
| `YOTCODE_API_LOG` | `CLAUDEPY_API_LOG` |
| `YOTCODE_SHELL` | `CCPY_SHELL` / `CLAUDEPY_SHELL` |

## 3. 连接模型

### 3.1 配置优先级

从低到高，后面的覆盖前面的：

1. 代码内置默认值；
2. `~/.yotcode/settings.json`；
3. `<项目>/.claude/settings.json`；
4. `<项目>/.yotcode/settings.json`；
5. `<项目>/.claude/settings.local.json`；
6. `<项目>/.yotcode/settings.local.json`；
7. 命令行参数（`--model`、`--provider`、`--api-key`、`--base-url` 等）。

`permissions.allow/deny/ask` 和 `hooks` 是**追加合并**的，所以全局 deny 规则不会被项目配置清掉。

设置文件支持 `//` 和 `/* */` 注释（JSONC）。

### 3.2 凭据从哪里找

优先级：

1. 真实环境变量；
2. 项目根目录 `.env`；
3. `~/.yotcode/.env`；
4. `settings.json` 里的 `env` 字段；
5. `settings.json` 里的 `providers.*.apiKey`。

真实环境变量永远优先，避免仓库里的 `.env` 意外覆盖 shell 中已经导出的值。

`.env` 示例（项目根目录）：

```dotenv
# Anthropic
# ANTHROPIC_API_KEY=sk-ant-...

# OpenAI 官方
# OPENAI_API_KEY=sk-...

# DeepSeek（会自动补 base URL）
# DEEPSEEK_API_KEY=sk-...

# 通义千问 / 百炼
# DASHSCOPE_API_KEY=sk-...

# Kimi / Moonshot
# MOONSHOT_API_KEY=sk-...

# 智谱 GLM
# ZHIPUAI_API_KEY=sk-...
```

> `.env` 已被 `.gitignore` 忽略。不要把 Key 写进 `settings.json` 后提交。

### 3.3 供应商是怎么选的

解析顺序：

1. `--provider anthropic|openai`；
2. 环境变量 `CCPY_PROVIDER`；
3. `settings.json` 的 `provider`；
4. 模型名猜测（`deepseek-*`、`gpt-*`、`o3` 等 → openai；`claude-*` → anthropic）；
5. 哪个 Key 存在。

注意：

- **同时配置 Anthropic 和 OpenAI Key 时，默认选 Anthropic。**
- 想用 GPT / DeepSeek，请显式加 `--provider openai`，或在 settings 里写 `"provider": "openai"`。
- 只设置 `DEEPSEEK_API_KEY` 时，会自动使用 `https://api.deepseek.com/v1` 和 `deepseek-chat`，不需要再写 base URL。
- 只设置 `DASHSCOPE_API_KEY` / `MOONSHOT_API_KEY` / `ZHIPUAI_API_KEY` 时，也会自动补对应 base URL。
- 本地地址（`localhost`、`127.0.0.1`、`::1`）即使没有 Key 也允许启动，适合 Ollama / vLLM / LM Studio。

### 3.4 DeepSeek 完整示例

#### 方式 A：`.env` + 命令行（最简单）

项目根目录 `.env`：

```dotenv
DEEPSEEK_API_KEY=sk-你的Key
```

运行：

```bat
run.cmd --model deepseek-chat
```

如果同时存在 `ANTHROPIC_API_KEY`，加上 provider：

```bat
run.cmd --provider openai --model deepseek-chat
```

推理模型：

```bat
run.cmd --provider openai --model deepseek-reasoner
```

`deepseek-reasoner` 的 `reasoning_content` 会显示在可折叠的 `thinking` 区域。

#### 方式 B：`settings.json`

把 `examples/settings.deepseek.json` 复制到 `.yotcode/settings.json`：

```jsonc
{
  "model": "deepseek-chat",
  "provider": "openai",
  "maxTokens": 8192,
  "autoCompact": true,
  "providers": {
    "openai": {
      "baseUrl": "https://api.deepseek.com/v1"
    }
  }
}
```

Key 仍然放在 `.env`：

```dotenv
DEEPSEEK_API_KEY=sk-你的Key
```

然后直接：

```bat
run.cmd
```

#### 方式 C：完全用环境变量

```bat
set DEEPSEEK_API_KEY=sk-你的Key
set CCPY_MODEL=deepseek-chat
set CCPY_PROVIDER=openai
run.cmd
```

### 3.5 OpenAI / GPT 完整示例

`.env`：

```dotenv
OPENAI_API_KEY=sk-你的Key
OPENAI_BASE_URL=https://api.openai.com/v1
```

运行：

```bat
run.cmd --provider openai --model gpt-4.1
```

常用模型：

| 模型 | 特点 |
|---|---|
| `gpt-4.1` | 100 万上下文，适合大仓库 |
| `gpt-4.1-mini` | 便宜、速度快 |
| `gpt-4o` | 通用多模态 |
| `gpt-4o-mini` | 轻量 |
| `o3` / `o4-mini` | OpenAI 推理模型 |

推理模型会自动使用 `max_completion_tokens`，不需要手动改参数。

`examples/settings.openai.json` 是完整 settings 示例。

### 3.6 Anthropic 官方

```dotenv
ANTHROPIC_API_KEY=sk-ant-你的Key
```

直接运行：

```bat
run.cmd
```

默认模型是 `claude-sonnet-4-5`。也可以：

## 4. 界面说明

新版界面参考 Claude Code 的深色终端风格：

```text
✻ yot  v0.1.0   ~/work/project             ● main  deepseek-chat · 128k  ^P
│
│  ❯ 把这个 bug 修一下，并补一个测试
│
│  ⏺ 我先看一下相关代码，然后修改 provider 的流式解析。
│  └ Read  yotcode/providers/openai_compat.py                    ✓ 0.3s
│    ⎿     118  def _is_openai_reasoning_model(model: str) -> bool:
│          119      """OpenAI 自家推理模型..."""
│
│  ⏺ 已经定位到问题，准备修改这两处。
│  ┌─ diff ──────────────────────────────────────────────── +3 −1 ┐
│  │ -            body["max_tokens"] = max_tokens                  │
│  │ +            if _is_openai_reasoning_model(self.model):       │
│  │ +                body["max_completion_tokens"] = max_tokens   │
│  │ +            else:                                            │
│  │ +                body["max_tokens"] = max_tokens              │
│  └───────────────────────────────────────────────────────────────┘
│
╭─────────────────────────────────────────────────────────────────────────╮
│ ❯ 输入消息…                                                         ⏎  │
╰─────────────────────────────────────────────────────────────────────────╯
 Ask anything, or type / for commands…
● default                    12.3k in / 4.1k out · ctx ███░░░░░░ 34% · ? help
```

### 4.1 顶部栏

从左到右：

- `✻ yot v0.1.0`：品牌和版本；
- 当前工作目录（过长会截断）；
- `● main`：Git 分支胶囊（不是 Git 仓库时隐藏）；
- `deepseek-chat · 128k`：当前模型和上下文窗口；
- `^P`：命令面板快捷键提示。

### 4.2 对话时间线

左侧有一条极淡的竖线，用来把多轮对话串起来。

- `❯`：用户消息；
- `⏺`：助手消息；
- `✻ thinking`：可折叠的思考过程；
- `└`：工具调用；
- `⎿`：工具输出。

### 4.3 工具行

工具调用压缩成一行：

```text
└ Read  src/app.py                                      ✓ 0.4s
```

- 工具名按类别着色：读取蓝色、编辑紫色、Bash 绿色、网页青色；
- 参数过长会截断；
- 右侧显示状态：`✓` 成功、`✕` 失败、`◐` 运行中、`◌` 等待权限；
- 点击这一行可以展开/折叠输出。

### 4.4 diff 卡片

编辑文件时显示真正的卡片：

- 顶部是文件名和 `+n −m`；
- 新增行有淡绿色背景，删除行有淡红色背景；
- 默认最多显示 40 行，点击工具行或按 `Ctrl+O` 展开；
- 权限确认弹窗里也会显示同样的 diff。

### 4.5 输入区

- 圆角细边框，聚焦时边框变成陶土橙；
- 左侧 `❯` 前缀；
- 右侧 `⏎` 是发送按钮，可以点击；
- 下方一行提示会随输入内容变化：
  - 空输入：`Ask anything, or type / for commands…`
  - 普通输入：`Enter send · Shift+Enter newline · @ files · ? help`
  - `/` 开头：`↑↓ choose · Tab complete · Enter run · Esc closes`
  - `!` 开头：`Bash mode · Enter runs immediately`
  - `#` 开头：`Memory mode · Enter appends to CLAUDE.md`

### 4.6 任务面板

模型调用 `TodoWrite` 后，输入框上方会出现任务带：

```text
✻ Tasks  ▰▰▰▱▱▱▱▱▱▱  1/3
  ☒ 阅读项目结构
  ◐ 实现功能
  ☐ 运行测试
```

可以用 `/todos` 重新显示，或 `Ctrl+T` 切换。

### 4.7 状态栏

左下角显示当前权限模式：

- `● default`
- `● ⏵⏵ accept edits`
- `● ◇ plan`
- `● ⚠ bypass`

右下角显示：

- 累计输入/输出 token；
- 估算费用（有价格数据时）；
- 上下文占用条 `ctx ███░░░░░ 34%`；
- `? help` 提示。

> 终端无法改变字号。如果觉得字太大，请在 Windows Terminal / iTerm2 / GNOME Terminal 里调小字体。推荐使用 `Cascadia Code`、`JetBrains Mono` 或 `Sarasa Mono SC`，并确保有中文回退字体。

## 5. 日常操作

### 5.1 发送与多行

- `Enter`：发送；
- `Shift+Enter` 或 `Ctrl+J`：换行；
- 直接粘贴多行文本也可以；
- 输入框会随内容自动增高，最多 10 行。

> 如果某些终端把 `Shift+Enter` 识别成普通 `Enter`，请用 `Ctrl+J` 换行，或者在终端设置里绑定 `Shift+Enter` 发送 `\n`。

### 5.2 `@文件`

在消息里写 `@路径`，YotCode 会把文件内容附加到提示词：

```text
请解释 @yotcode/providers/openai_compat.py 的流式解析流程
```

输入 `@` 后会弹出文件补全，`Tab` 接受，`↑↓` 选择。

发送时会按扩展名智能分流：

- `@图片.png`：作为真正的图片发送给模型，模型能"看到"画面内容；
- `@代码.py`：文本按原来的 `<file>` 包装附加，提示词保持一致；
- 其他二进制文件：给出说明文本，避免乱码。

四种发送图片/文件的方式见 [5.8 发送图片和文件](#58-发送图片和文件)。

### 5.3 `!命令`

以 `!` 开头的输入会直接执行 shell 命令，不经过模型：

```text
!git status
!python -m pytest -q
```

注意：`!` 命令会直接通过 Bash 工具执行，**不会弹权限确认**。执行前请确认命令安全。

### 5.4 `#笔记`

以 `#` 开头的输入会追加到项目根目录的 `CLAUDE.md`：

```text
# 这个项目的测试命令是 python -m pytest
```

下次启动时，这条记忆会自动加载。

### 5.5 斜杠命令

```text
/help
```

查看全部命令、快捷键和自定义命令。

常用命令：

| 命令 | 作用 |
|---|---|
| `/help` | 帮助 |
| `/clear` | 开始新对话（会话 id 不变，写入 reset 事件） |
| `/compact [说明]` | 压缩上下文 |
| `/cost` | token 与费用 |
| `/status` | 模型、目录、权限、会话 |
| `/doctor` | 环境检查 |
| `/model [名字]` | 切换模型 |
| `/config` | 显示设置文件和生效值 |
| `/permissions` | 显示权限规则 |
| `/memory` | 显示加载的 CLAUDE.md |
| `/init` | 分析仓库并创建/更新 CLAUDE.md |
| `/todos` | 显示任务列表 |
| `/agents` | 列出子代理 |
| `/skills` | 列出技能包（Skill） |
| `/checkpoints` | 列出本次会话的文件检查点 |
| `/revert [id]` | 回退到某个检查点（不带 id 列最近几个让你选） |
| `/mcp` | MCP 服务器状态 |
| `/resume` | 打开会话选择器 |
| `/export [路径]` | 导出 Markdown |
| `/add-dir <路径>` | 本次会话允许访问另一个目录 |
| `/exit` | 退出 |

**补全面板怎么用**：输入 `/` 会弹出命令列表；`↑` / `↓` 移动高亮项，
`Tab` 或**回车**都会把高亮的那一项补全到输入框里（不会直接发出去）。
补全完再按一次回车才真正执行。

> 补全面板开着时，回车 = "选中当前高亮项"，这是和普通输入框不一样的地方。
> 如果你想原样发送刚输入的文本（比如 `/x` 是个不存在的命令），
> 先把输入框里的内容改成和任何命令都不匹配的样子（补全面板会自动收起），
> 再按回车。

### 5.6 快捷键

| 按键 | 作用 |
|---|---|
| `Enter` | 发送 |
| `Shift+Enter` / `Ctrl+J` | 换行 |
| `Esc` | 打断当前回答 |
| `Ctrl+C` | 打断；空闲时清空输入；再按一次退出 |
| `Ctrl+D` | 输入为空时退出 |
| `Shift+Tab` | 循环权限模式 |
| `Ctrl+P` | 命令面板 |
| `Ctrl+R` | 会话选择器 |
| `Ctrl+V` / `Ctrl+Shift+V` | 从剪贴板附加截图 |
| `Ctrl+O` | 展开/折叠工具输出 |
| `Ctrl+L` | 清屏（上下文保留） |
| `Ctrl+T` | 显示/隐藏任务 |
| `F1` | 帮助 |
| `?` | 输入框为空时打开帮助 |
| `Tab` | 接受斜杠命令或文件补全 |
| `↑` / `↓` | 历史消息 / 补全列表 |

### 5.7 打断、清空和退出

- 回答生成中按 `Esc`：立即取消当前请求和工具；
- 按 `Ctrl+C`：有输入时清空输入，空闲时退出；
- `/clear`：清空对话上下文和任务，开始新话题；
- `Ctrl+L`：只清屏，不清上下文；
- `/exit` 或 `Ctrl+D`：退出。

### 5.8 发送图片和文件

除了文字，截图、图片和文件也能一起发给模型。四种入口最终都会变成一条带附件的用户消息：

| 入口 | 操作 | 适用场景 |
| --- | --- | --- |
| 命令行参数 | `yot -p "解释这张图" --image shot.png` | 无头模式 / 脚本 |
| 剪贴板截图 | 输入框按 `Ctrl+V`（或 `Ctrl+Shift+V`） | 截图后直接发给模型 |
| `@文件` 智能识别 | 输入 `@图片.png` 或 `@代码.py` | 在消息里引用文件 |
| 粘贴 / 拖放路径 | 把文件路径粘贴或拖进输入框 | 从资源管理器复制文件 |

**1. 命令行附加（`--image` / `--file`）**

两个参数都可重复传多次，程序按扩展名自动分辨：图片（`png/jpg/jpeg/gif/webp/bmp/tif/tiff`）
读成图片块，其他文件读成文本块：

```bash
yot -p "这两张图有什么区别？" --image before.png --image after.png
yot -p "审查这个文件的改动" --file src/main.py
yot --image shot.png          # 交互 TUI 里带着图片启动
```

**2. 剪贴板截图（`Ctrl+V` / `Ctrl+Shift+V`）**

截图到剪贴板后，直接在输入框按 `Ctrl+V` 即可附加：终端无法随粘贴事件传位图，
此时粘贴内容为空，程序会自动读取系统剪贴板里的图片。也可以按 `Ctrl+Shift+V`
（部分终端用 `Ctrl+Alt+V`）显式读取剪贴板截图。粘贴普通文字/代码时仍按原样插入输入框，
不会误读剪贴板里的残留图片。Pillow 已作为必需依赖，`pip install` 后开箱即用；
读取失败会给出友好提示，不影响其他附件方式。

**3. `@文件` 智能识别**

输入 `@` 的补全方式不变；发送时按扩展名智能处理，详见 [5.2](#52-文件)：图片作为
真正的图片发送，文本沿用 `<file>` 包装，其他二进制给出说明文本。

**4. 粘贴 / 拖放文件路径**

从文件管理器复制文件（或把文件拖进终端窗口），输入框会自动把路径识别成附件，
不会把一长串路径文本发给模型。已附加的图片/文件显示为输入框下方的筹码，
点击 `×` 可在发送前移除。

**限制与注意事项**

- 单个文件上限 5MB（与内置 `Read` 工具读图片一致），一次最多 10 个附件；
- 文本附件超过 6 万字符会截断；
- 当前模型不支持图片时会打印警告，仍会发送，由模型端决定如何响应；
- 附件随会话写入 JSONL，恢复后仍可回放；
- 图片以 base64 进入请求体，超大图片会增加 token 消耗与费用。

## 6. 权限系统

### 6.1 四种模式

| 模式 | 行为 |
|---|---|
| `default` | 只读工具自动允许；写文件、执行命令前询问 |
| `acceptEdits` | 项目内写文件自动允许；Bash 等仍会询问 |
| `plan` | 只允许只读工具；模型只能调查和提出计划，不能修改 |
| `bypassPermissions` | 全部自动允许，最危险 |

> TUI 的 `Shift+Tab` 只在 `default` → `acceptEdits` → `plan` 之间循环；`bypassPermissions` 需要用 CLI 参数启动。

切换：

- TUI：`Shift+Tab`；
- CLI：`--permission-mode acceptEdits`；
- 简写：`--dangerously-skip-permissions` 等价于 `bypassPermissions`。

> `bypassPermissions` 只建议在容器、临时目录或你完全信任的仓库里使用。

#### acceptEdits 为什么删除文件还要确认？

`acceptEdits` 只放行**三个"改文件"工具**：`Write`、`Edit`、`MultiEdit`。
除此之外一律照常询问，包括：

- `Bash`（`rm`、`del`、Python 脚本……）
- `MultiEdit` 以外的任何写操作

这是**有意为之**，也和 Claude Code 的行为一致：`Bash` 能干任何事，
如果连它都自动放行，"acceptEdits"就等于"全部放行"了。

删除文件通常走的是 `Bash rm`，所以仍然会弹窗。弹窗里会明确告诉你这一点。

**想让它别再问**，有两个办法：

1. 弹窗里按 `a`（"Yes, and don't ask again"），会写成一条
   `Bash(rm:*)` 之类的规则存进 `.yotcode/settings.local.json`；
2. 自己在 `settings.json` 里加 allow 规则：

```jsonc
{
  "permissions": {
    "allow": [
      "Bash(rm:*)",
      "Bash(del:*)",
      "Bash(python:*)"
    ]
  }
}
```

> 更省事的做法：让 AI 用 `Write`/`Edit` 改文件（这两个在 acceptEdits 下直接放行），
> 只有真正需要删文件时才走 `Bash`。

### 6.2 规则写法

在 `settings.json` 里：

```jsonc
{
  "permissions": {
    "allow": [
      "Read(./src/**)",
      "Bash(npm test:*)",
      "Bash(git status)",
      "WebFetch(domain:github.com)"
    ],
    "ask": [
      "Bash(git push:*)",
      "Write(./.yotcode/**)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(rm -rf:*)"
    ],
    "additionalDirectories": ["../shared-lib"]
  }
}
```

规则格式：

```text
工具名
工具名(参数模式)
*
```

常见例子：

| 规则 | 含义 |
|---|---|
| `Bash` | 所有 Bash 命令 |
| `Bash(npm test:*)` | `npm test` 开头的命令 |
| `Bash(git push:*)` | `git push` 开头的命令 |
| `Read(./src/**)` | 项目内 `src` 下所有文件 |
| `Read(~/notes/*.md)` | 家目录笔记 |
| `Write` | 所有写文件 |
| `WebFetch(domain:github.com)` | 只允许抓取 GitHub 域名 |
| `*` | 所有工具 |

注意：

- `deny` 永远最高优先级；
- 评估顺序是：临时允许 → deny → bypass → plan → ask → allow → 工具默认；
- `Bash` 的复合命令（`&&`、`||`、`;`）要求每一段都匹配规则；
- Bash 规则只是前缀/通配匹配，不是完整的 shell 解析器，不要把它当安全沙箱。

### 6.3 “总是允许”

权限弹窗里选择 “always allow” 后，规则会写入：

```text
.yotcode/settings.local.json
```

下次启动仍然生效。想撤销就编辑这个文件。

### 6.4 `--allowedTools` 和权限规则的区别

- `--allowedTools "Read,Grep"`：**只把这两个工具暴露给模型**，是工具过滤；
- `permissions.allow`：工具可以用，但调用时是否自动放行，是权限决策。

两者可以一起用。

## 7. 内置工具

| 工具 | 作用 | 只读 |
|---|---|---|
| `Read` | 读取文本文件、图片 | 是 |
| `Write` | 写入/覆盖文件 | 否 |
| `Edit` | 精确字符串替换 | 否 |
| `MultiEdit` | 一次做多处替换 | 否 |
| `LS` | 列目录 | 是 |
| `Glob` | 按文件名模式查找 | 是 |
| `Grep` | 按内容搜索（优先 ripgrep） | 是 |
| `Bash` | 执行 shell 命令 | 否 |
| `BashOutput` | 读取后台命令输出 | 是 |
| `KillShell` | 结束后台命令 | 否 |
| `WebFetch` | 抓取网页并转文本 | 是 |
| `WebSearch` | 搜索网页 | 是 |
| `TodoWrite` | 更新任务列表 | 是 |
| `Task` | 启动子代理 | 是 |
| `TaskPlan` | 声明任务图，由代码编排并发执行 | 是 |
| `AskUserQuestion` | 向用户提问 | 是 |
| `ExitPlanMode` | 结束计划模式 | 是 |
| `Skill` | 加载技能包正文 | 是 |
| `mcp__*` | MCP 服务器提供的工具 | 依服务器 |

### 7.0 工具并发执行

模型一轮里可以同时请求多个工具。YotCode 会按工具性质分开处理：

| 类型 | 工具 | 执行方式 |
|---|---|---|
| 只读、无副作用 | `Read`、`LS`、`Glob`、`Grep`、`BashOutput`、`Skill` | **并发**执行，总耗时接近其中最慢的一个 |
| 互不干扰的独立任务 | `Task`（子代理） | **并发**执行，各自带独立上下文 |
| 任务图调度 | `TaskPlan`（任务编排） | 内部按依赖关系并发调度子代理，见 [12.4](#124-任务编排把一件事拆成带依赖的任务图) |
| 有副作用 | `Write`、`Edit`、`MultiEdit`、`Bash`、`KillShell` | 严格**按顺序**执行，避免两个写操作抢同一个文件 |

要点：

- 回填给模型的 `tool_result` 顺序**始终和模型请求的顺序一致**，并发只是内部提速，不影响协议；
- 权限弹窗一次只弹一个：并发时"询问用户"这一步会被排队，工具本身照常并发；
- 想真正用上并发，就让模型**一轮里发多个互不相关的调用**（例如"同时读 3 个文件"、"同时派 3 个子代理查 3 个目录"），而不是一轮一个地挤牙膏。

### 7.1 Bash 的 shell

Windows 上：

- 如果找到 Git Bash，优先使用它，所以 `ls`、`grep`、`&&` 等命令可用；
- 否则回退到 PowerShell；
- 可以用 `CCPY_SHELL` 或 settings 的 `shell` 指定，例如：

```jsonc
{
  "shell": "C:/Program Files/Git/bin/bash.exe"
}
```

### 7.2 后台命令

Bash 工具支持 `run_in_background=true`。后台输出写到：

```text
~/.yotcode/tmp/bash_xxxxxxxx.log
```

模型随后可以用 `BashOutput` 增量读取，或用 `KillShell` 结束。

### 7.3 网页搜索

`WebSearch` 默认使用 DuckDuckGo。想获得更稳定的结果，可以配置：

```dotenv
BRAVE_API_KEY=...
# 或
TAVILY_API_KEY=...
```

也可以在 settings 里指定：

```jsonc
{
  "webSearch": {
    "provider": "brave"
  }
}
```

`WebFetch` 会把 HTML 转成可读文本，并缓存本次会话的抓取结果。

## 8. 会话与恢复

### 8.1 会话存在哪里

```text
~/.yotcode/projects/<目录 slug>/<session-id>.jsonl
~/.yotcode/projects/<目录 slug>/<session-id>.meta.json
```

每个事件一行 JSON：

- `{"type":"message", ...}`：一条消息；
- `{"type":"todos", ...}`：任务列表；
- `{"type":"usage", ...}`：token 和费用；
- `{"type":"model", ...}`：模型切换；
- `{"type":"reset", "reason":"clear"}`：`/clear` 或压缩；
- `{"type":"compaction", "summary": ...}`：压缩摘要。

恢复时按顺序回放，遇到 `reset` 就清空之前的内容。

### 8.2 恢复方式

```bat
run.cmd --continue              :: 继续当前目录最近的会话
run.cmd --resume                :: 弹出会话选择器（类似 claude -r）
run.cmd --resume <session-id>   :: 按 id 精确恢复（可跨项目）
run.cmd --session <session-id>  :: 指定会话
run.cmd --list-sessions         :: 列出当前目录的会话
```

**`--resume` 不带 id 时会弹出文本会话选择器**：终端列出当前目录的会话
（日期、标题、轮数），输入序号回车确认。这样即使是几天前的会话也能找回来，
而不像以前只能取最近一条。带 id 时仍按 id 精确恢复，并可跨项目加载。
没有 TTY 的环境（如管道、CI）会自动退化为"打印列表 + 读取序号"，不会挂起。

TUI 里：

```text
/resume
```

打开图形化会话选择器；`Ctrl+R` 也可以。两种入口都能恢复历史会话。

> 会话里的图片附件也会一起恢复：之前带图发送的消息在回放时仍显示图片标记。

### 8.3 导出

```text
/export
/export ./report.md
```

导出为 Markdown，包含用户/助手消息和工具调用。不写路径时会生成
`yotcode-session-<时间戳>.md`。

### 8.4 `/clear` 和 `/compact` 的区别

- `/clear`：清空对话上下文和任务，开始新话题；会话 id 不变；
- `/compact`：把旧对话总结成摘要，保留最近消息，继续当前任务。

## 11. 自定义斜杠命令

### 11.1 放在哪里

- `<项目>/.yotcode/commands/*.md`
- `<项目>/.claude/commands/*.md`
- `~/.yotcode/commands/*.md`
- `~/.claude/commands/*.md`

项目命令直接用 `/名字`；用户目录命令带 `user:` 前缀，例如 `/user:review`。

子目录会形成命名空间，例如：

```text
.yotcode/commands/db/migrate.md  ->  /db/migrate
```

### 11.2 文件格式

```markdown
---
description: 为指定文件生成单元测试
argument-hint: <文件路径>
---

请为 $ARGUMENTS 生成 pytest 单元测试。

先阅读这个文件：

@$ARGUMENTS

要求：
- 覆盖正常路径和边界条件
- 使用项目现有的 fixture
- 不要修改业务代码
```

### 11.3 变量和插值

| 写法 | 作用 |
|---|---|
| `$ARGUMENTS` | 命令后的完整参数 |
| `$1` … `$9` | 按空格拆分后的第 n 个参数 |
| `` !`命令` `` | 先执行 shell，把输出插入提示词 |
| `@文件` | 把文件内容插入提示词 |

例子：

```markdown
---
description: 查看当前分支和测试状态
---

当前分支：

!`git branch --show-current`

最近提交：

!`git log --oneline -5`

请总结现在应该先做什么。
```

### 11.4 查看命令

```text
/help
```

会列出所有内置命令和自定义命令。

> 当前版本会读取 frontmatter 里的 `description`、`argument-hint`、`model` 等字段，但只有 `description` 和 `argument-hint` 会直接显示在帮助里；`model` 和 `allowed-tools` 还没有真正应用到命令执行。不要把安全限制只寄托在命令 frontmatter 上。

## 12. 子代理

子代理有独立的上下文窗口，适合：

- 搜索整个仓库；
- 独立调查一个模块；
- 并行做只读分析；
- 避免大量搜索结果污染主对话。

### 12.1 内置子代理

| 名称 | 能力 |
|---|---|
| `general-purpose` | 所有工具 |
| `Explore` | 只读工具，适合搜索和理解代码 |

模型通过 `Task` 工具调用它们。

### 12.2 自定义子代理

放在：

- `.yotcode/agents/*.md`
- `.claude/agents/*.md`
- `~/.yotcode/agents/*.md`
- `~/.claude/agents/*.md`

例子：

```markdown
---
name: test-runner
description: 只负责运行测试并分析失败原因
tools: Read, Grep, Bash
model: deepseek-chat
---

你是一个测试分析专家。

只运行测试和读取代码，不要修改文件。
失败时给出：
1. 失败测试名
2. 根本原因
3. 建议的修复位置
```

如果 `tools` 全是只读工具，会被标记为 read-only。

查看：

```text
/agents
```

### 12.3 并行派多个子代理

同一轮里发多个 `Task` 调用，它们会**真正并发**执行（各自独立上下文、各自独立调模型）：

```text
同时派三个 Explore 子代理：
1. 查清楚 yotcode/agent.py 的主循环是怎么调度工具的
2. 查清楚 yotcode/ui/ 下的界面组件有哪些，分别负责什么
3. 查清楚权限系统 permissions.py 的判定顺序
```

模型会开三个子代理同时跑，总耗时接近其中最慢的那个，而不是三个相加。

> 注意：子代理共享同一个工作目录。如果两个子代理同时改同一个文件，仍然可能冲突 ——
> 让它们各查各的目录，或者一个只读、一个可写。

### 12.4 任务编排：把一件事拆成带依赖的任务图

前面讲的是「手动派几个子代理」。如果一件大事能拆成好几块、而且块与块之间有先后关系，
可以让模型一次性声明整张**任务图**，剩下的交给代码调度。

模型会调用 `TaskPlan` 工具，形如：

```json
{
  "tasks": [
    {"id": "a", "title": "查清鉴权模块", "prompt": "读 yotcode/permissions.py，说明判定顺序"},
    {"id": "b", "title": "查清界面模块", "prompt": "读 yotcode/ui/，列出组件和职责"},
    {"id": "c", "title": "汇总成改造方案",
     "prompt": "基于前两个调查结果，给出改造清单",
     "depends_on": ["a", "b"]}
  ]
}
```

调度器会这样跑：

| 能力 | 行为 |
|---|---|
| **依赖关系** | `c` 依赖 `a`、`b`，所以必须等两个都完成 |
| **自动调度** | 每一轮挑出所有"依赖已满足"的任务，**并发**执行 |
| **结果传递** | 上游任务的报告会拼进下游任务的提示词里（`c` 能直接看到 `a`、`b` 的结论） |
| **失败重试** | 某个任务失败会自动重试（默认 2 次，最多 5 次） |
| **失败传播** | 依赖失败任务的下游直接标记为"跳过"，不会白跑 |
| **任务 → 子代理绑定** | 每个任务默认交给一个子代理执行（有独立上下文，不污染主对话） |

调度过程是这样：

```
第 1 轮：就绪 = [a, b]        → 并发执行
第 2 轮：就绪 = [c]           → a、b 的报告注入 c 的提示词后执行
汇总：把每个任务的状态和报告整理成一份，返回给主模型
```

和 `TodoWrite` 的区别：

| | `TodoWrite` | `TaskPlan` |
|---|---|---|
| 作用 | 记录"接下来要做哪几件事"，给用户看 | 真的去执行这些事 |
| 依赖关系 | 无 | 支持 `depends_on` |
| 谁来干活 | 主代理自己按顺序做 | 子代理并发做 |
| 失败处理 | 无 | 自动重试 + 跳过下游 |

> 提示：任务提示词要**自包含**——子代理看不到你和主模型的对话，
> 所以"查清楚 X 在哪、怎么用的"这类描述要写全，必要时直接给出文件路径线索。

## 13. Skill 技能包

Skill 用来把**一套可复用的流程或知识**写成文件，让模型按需加载。

它和项目记忆（`CLAUDE.md`）的区别：

| | CLAUDE.md 记忆 | Skill 技能包 |
|---|---|---|
| 加载方式 | **无条件全量**塞进系统提示词 | 只放名字和描述，**正文按需加载** |
| 什么时候进上下文 | 每次启动都在 | 只有模型判断相关时才读进来 |
| 适合放什么 | 项目背景、约定、命令 | 一套具体流程，比如"发布流程""写迁移的步骤" |

项目一大，`CLAUDE.md` 会又长又吵，而且模型分不清哪段和当前任务有关。
Skill 把它拆成一个个独立小包，由模型自己决定要不要打开 —— 这叫**渐进式披露**。

### 13.1 放在哪里

```text
.yotcode/skills/<名字>/SKILL.md     项目级（推荐）
.claude/skills/<名字>/SKILL.md       项目级
~/.yotcode/skills/<名字>/SKILL.md   用户级（所有项目都能用）
~/.claude/skills/<名字>/SKILL.md     用户级
```

同名时**项目级覆盖用户级**。

也支持把技能直接写成 `.yotcode/skills/<名字>.md`（不用建子目录）。

### 13.2 文件格式

```markdown
---
name: release
description: 发布流程：跑测试、打 tag、写 changelog。涉及发版或打 tag 时使用。
allowed-tools: Bash, Read
---

# 发布流程

按顺序执行，**不要跳步**：

1. 先跑测试：`python -m pytest -q`
2. 全绿后再更新 CHANGELOG
3. 打 tag：`git tag -a v0.2.0 -m "release"`

@scripts/release.py
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 否 | 缺省用目录名 |
| `description` | **强烈建议** | 模型判断"要不要加载这个 skill"的**唯一依据**，要写清"什么时候该用它" |
| `allowed-tools` | 否 | 建议这个 skill 使用的工具，会随正文一起交给模型（目前只做提示，不强制拦截） |

正文里可以单独一行写 `@相对路径` 导入别的文件（相对 SKILL.md 所在目录，最多递归两层）。

### 13.3 怎么用

1. 把 skill 文件放好；
2. 启动程序，系统提示词里会自动带上 skill 清单（只有名字和描述，很省 token）；
3. 模型遇到相关任务时会自动调用 `Skill` 工具把正文读进来并照着做。

查看当前可用的 skill：

```text
/skills
```

> 新增或修改 skill 后需要**重启程序**，因为系统提示词只在启动时构建一次。
> `/skills` 命令则是实时扫描的，可以先用它确认文件放对了没有。

### 13.4 什么时候该用 Skill

- **发布流程**：打 tag、发版、检查清单；
- **特定技术栈的约定**：比如"这个仓库的新增接口必须怎么写测试"；
- **排查手册**：某个模块常见故障的定位步骤；
- **一次性的大段参考资料**：放在正文里按需加载，而不是塞进 `CLAUDE.md` 常驻。

## 14. 检查点与回退

AI 编程助手最让人抓狂的场景就是"它把你的代码改坏了"。
检查点就是为此存在的：**任何会改文件的操作执行前，先把原文件内容存一份**，
之后一条命令就能退回去。

### 14.1 自动留检查点

不需要配置。只要 AI 用 `Write` / `Edit` / `MultiEdit` 改了文件，
**改动之前**的原始内容就会被自动存下来。

存放位置（都在项目里，不污染用户主目录）：

```text
<项目>/.yotcode/checkpoints/<会话ID>/<检查点ID>/
    meta.json      元信息：时间、哪个工具改的、涉及哪些文件
    blobs/0.txt    每个文件改之前的内容
```

按**会话**分目录：检查点只回退"这次会话里改的东西"，不会误伤你之前就有的工作。

保留策略：每个会话最多留 **50** 个检查点，超出的从旧到新自动删掉。

### 14.2 查看检查点

```text
/checkpoints
```

输出示例：

```text
共 3 个检查点（新的在前）：

- cf118b4a058c  2026-11-19 10:13:32  Write  demo.py
- 3b7e0c91aa42  2026-11-19 10:12:05  Edit   src/api.py
- 90fa4d2c6e18  2026-11-19 10:11:20  MultiEdit  config.toml

用 /revert <检查点ID> 恢复指定的那一次改动；直接 /revert 则回退最近一次。
```

### 14.3 回退

```text
/revert                # 回退最近一次改动
/revert cf118b4a058c   # 回退指定的那一次
```

恢复规则：

- 文件改之前**就存在** → 把旧内容写回去；
- 文件改之前**不存在**（是这次新建的）→ 直接删掉。

回退完会明确告诉你动了哪些文件：

```text
已回退到检查点 cf118b4a058c（2026-11-19 10:13:32，Write）
已恢复（写回改前内容）：
  - D:\work\demo.py
已删除（改之前不存在）：
  - D:\work\new_file.py
```

> **注意**：回退只改**这一个检查点记录的文件**。如果 AI 在那次之后又改了同一个文件，
> 回退会把它一起覆盖成旧内容——回退前建议先看一眼 `/checkpoints` 的列表。

### 14.4 关掉检查点

检查点会占磁盘。不想用可以在 `settings.json` 里关掉：

```json
{
  "ui": {
    "checkpoints": false
  }
}
```

关掉之后 `/revert` 就没东西可退了。

### 14.5 什么时候用

- AI 改完代码你觉得**改错了**，想让它换个思路重来 → `/revert`；
- AI 一次改了好几个文件，其中某个改砸了 → `/revert <id>` 精确退那一次；
- 想看看 AI 一共动过哪些文件 → `/checkpoints`。

> 想要更强的保护（比如连命令执行也能退），需要用 Git 管理仓库 ——
> 检查点只覆盖**文件内容**，不覆盖 Git 历史。

## 15. Hooks

Hooks 是在 Agent 生命周期里执行的外部命令。

实际由 Agent 触发的事件：

- `UserPromptSubmit`
- `PreToolUse`
- `PostToolUse`
- `Stop`
- `SessionEnd`

### 15.1 配置

```jsonc
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "command": "python .yotcode/check_command.py",
            "timeout": 10
          }
        ]
      }
    ],
    "UserPromptSubmit": [
      {
        "command": "python .yotcode/add_context.py"
      }
    ]
  }
}
```

也支持简化写法：

```jsonc
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash", "command": "python .yotcode/check_command.py" }
    ]
  }
}
```

### 15.2 输入和输出

Hook 从 stdin 收到 JSON，例如：

```json
{
  "event": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "git push" },
  "cwd": "C:/work/project"
}
```

规则：

- 退出码 `0`：继续；
- 退出码 `2`：阻止操作（`PreToolUse` 场景）；
- 其他非零：记录错误，但通常不阻止；
- `UserPromptSubmit` / `PreToolUse` 的 stdout 会作为额外上下文注入；
- 超时会终止 hook，`PreToolUse` 超时会阻止操作。

### 15.3 示例：阻止危险的 git push

`check_command.py`：

```python
import json
import sys

payload = json.load(sys.stdin)
command = payload.get("tool_input", {}).get("command", "")

if "git push" in command:
    print("不要自动 push，请先让用户确认。", file=sys.stderr)
    sys.exit(2)

print("ok")
```

环境变量 `CLAUDE_PROJECT_DIR` 会指向项目根目录。

## 16. MCP 服务器

MCP（Model Context Protocol）服务器通过 stdio 接入。

### 16.1 配置

```jsonc
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "C:/work/project"
      ],
      "env": {
        "SOME_TOKEN": "..."
      }
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_..."
      }
    }
  }
}
```

字段：

- `command`：可执行文件；
- `args`：参数数组；
- `env`：额外环境变量。

### 16.2 工具命名

MCP 工具会以：

```text
mcp__服务器名__工具名
```

的形式出现在模型工具列表里。

### 16.3 查看状态

```text
/mcp
```

启动失败时，stderr 会写到：

```text
.yotcode/mcp-<服务器名>.log
```

### 16.4 注意

- 当前只支持 **stdio** MCP 服务器；
- 需要本机有 `npx` / `uvx` / Python 等运行环境；
- 服务器启动可能较慢，首次连接会等待最多 25 秒；
- MCP 工具同样受权限系统管理。

## 17. 无头模式与脚本

### 17.1 基本用法

```bat
run.cmd -p "解释这个仓库的架构"
```

`-p` / `--print` 表示非交互：输出结果后退出。

也可以：

```bash
echo "运行测试并总结失败原因" | yot -p
```

无头模式也能附加图片/文件，`--image` 与 `--file` 都可重复传：

```bash
yot -p "解释这张截图" --image ./shot.png
yot -p "对比两张图" --image before.png --image after.png
yot -p "总结这个文件" --file ./report.md
```

按扩展名自动转换：图片走图片块，其他文件读成文本块。限制见 [5.8](#58-发送图片和文件)。

### 17.2 输出格式

```bat
run.cmd -p --output-format text "总结 README"
run.cmd -p --output-format json "总结 README"
run.cmd -p --output-format stream-json "总结 README"
```

- `text`：纯文本，默认；
- `json`：最后输出一个结果对象；
- `stream-json`：逐行输出事件，最后再输出 result。

`json` 结果包含：

```json
{
  "type": "result",
  "subtype": "success",
  "result": "最终回答",
  "session_id": "20261117-...",
  "duration_ms": 12345,
  "num_turns": 3,
  "usage": { "input_tokens": 0, "output_tokens": 0 },
  "total_cost_usd": 0.0123
}
```

### 17.3 非交互权限

无头模式无法弹窗。默认情况下，需要确认的工具会被拒绝。

三种做法：

1. 只使用只读工具；
2. 在 settings 的 `permissions.allow` 里提前放行；
3. 使用：

```bat
run.cmd -p --permission-mode acceptEdits "..."
run.cmd -p --dangerously-skip-permissions "..."
```

> `--allowedTools "Read,Grep"` 只是过滤工具，不会自动批准写文件或 Bash。

### 17.4 退出码

| 退出码 | 含义 |
|---|---|
| `0` | 正常 |
| `1` | 配置/参数错误 |
| `130` | 被 Ctrl+C 中断 |

适合放进 CI：

```bash
yot -p --output-format json "检查代码并生成摘要" > result.json
```

## 20. 常见问题

### 20.1 启动提示 “No model API key configured”

原因：没有找到可用 Key。

检查：

1. 是否在**项目根目录**运行 `run.cmd` / `yot`；
2. `.env` 是否真的存在，变量名是否拼对；
3. 是否在错误的 shell 里设置了环境变量；
4. 想先体验可以运行 `run.cmd --mock`。

### 20.2 DeepSeek 报 404

检查 base URL：

```text
https://api.deepseek.com/v1
```

注意末尾的 `/v1`。模型名使用 `deepseek-chat` 或 `deepseek-reasoner`。

### 20.3 OpenAI 报 `max_tokens` 不支持

YotCode 会对 `o1/o3/o4/gpt-5` 自动使用 `max_completion_tokens`。如果你用的是自定义网关，它可能既不支持 `max_completion_tokens` 也不支持 `max_tokens`，请查看网关文档。

### 20.4 同时有两个 Key，结果走了 Anthropic

这是设计行为。显式指定：

```bat
run.cmd --provider openai --model gpt-4.1
```

或在 settings 里写：

```jsonc
{ "provider": "openai" }
```

### 20.5 Ollama 没有 Key，启动却说没配置

必须让 provider 走 OpenAI 兼容协议。最稳妥：

```bat
run.cmd --provider openai --base-url http://localhost:11434/v1 --model qwen2.5-coder
```

如果只用 `.env`，加上：

```dotenv
CCPY_PROVIDER=openai
CCPY_MODEL=qwen2.5-coder
OPENAI_BASE_URL=http://localhost:11434/v1
```

### 20.6 Windows 中文乱码

- 用 `run.cmd` 启动，它会执行 `chcp 65001`；
- 或在 PowerShell 里：

```powershell
$env:PYTHONUTF8=1
chcp 65001
```

- 终端字体要有中文回退（例如 `Sarasa Mono SC`、`Microsoft YaHei Mono`）。

### 20.7 符号显示成方块或 “L”

`❯`、`⏺`、`└`、`⎿`、`▰` 需要终端字体支持。推荐：

- `Cascadia Code` / `Cascadia Mono`
- `JetBrains Mono`
- `Sarasa Mono SC`
- `Fira Code` + 中文回退字体

如果仍然缺字，可以在 Windows Terminal 设置里换字体。

### 20.8 按 Enter 没反应

当前版本已修复输入框 owner 引用问题。请确认：

- 焦点在输入框内（点击一下输入区）；
- 不是在有补全弹窗时按 Enter（此时 Enter 仍然发送，Tab 才是补全）；
- 终端没有把 Enter 映射成其他按键。

### 20.9 权限弹窗一直拒绝

无头模式不会弹窗。交互模式下如果一直拒绝：

- 检查 `.yotcode/settings.local.json` 里是否有 `deny` 规则；
- `/permissions` 查看规则；
- 换 `--permission-mode acceptEdits` 或手动选择 “always allow”。

### 20.10 上下文太长

```text
/compact
```

或降低：

```jsonc
{ "compactThreshold": 0.7 }
```

也可以 `/clear` 开新话题。

### 20.11 会话找不到

会话按**当前工作目录**分组。请在同一个目录下运行：

```bat
run.cmd --list-sessions
```

如果改过目录名，slug 会变，旧会话不会出现在新目录下。

### 20.12 `!命令` 为什么没弹权限

这是设计行为：`!` 是用户直接执行 shell，不经过模型。请自行确认命令安全。

### 20.13 代理/网关返回 401

- `--api-key` 是否传给了正确的 provider；
- 自定义网关是否要求 `Authorization: Bearer ...`；
- 同时设置 `OPENAI_API_KEY` 和 `OPENAI_BASE_URL`；
- 某些网关需要 `ANTHROPIC_AUTH_TOKEN` 而不是 `ANTHROPIC_API_KEY`。

## 21. 开发与测试

### 21.1 安装开发依赖

```bash
python -m venv .venv
. .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
```

### 21.2 运行测试

```bash
python -m pytest
python scripts/smoke.py
python scripts/ui_smoke.py
python scripts/ui_interactions.py
```

- `pytest`：类型、配置、权限、会话、工具、provider 转换；
- `scripts/smoke.py`：无头 Agent + 工具；
- `scripts/ui_smoke.py`：Textual 挂载、模态框、截图；
- `scripts/ui_interactions.py`：快捷键、补全、命令、恢复、`/clear`。

### 21.3 生成界面预览

```bash
python scripts/ui_preview.py
python scripts/ui_modals.py
```

会生成 SVG，可用浏览器打开。

### 21.4 目录结构

```text
yotcode/
  agent.py         Agent 主循环：流式、工具、权限、压缩、子代理
  cli.py           命令行入口 + 无头模式
  config.py        设置合并、凭据、模型/供应商解析
  attachments.py   图片/文件附件转换：路径/剪贴板 → 内容块，大小与类型校验
  permissions.py   allow/ask/deny 规则
  session.py       JSONL 会话
  types.py         Anthropic 风格消息模型
  checkpoints.py   文件快照与恢复（/checkpoints、/revert）
  tasks.py         任务图模型：依赖、环检测、就绪集
  providers/       anthropic.py / openai_compat.py / mock.py
  tools/           文件、Shell、网页、任务、MCP
  ui/              app.py / widgets.py / render.py / modals.py / theme.tcss
tests/             离线测试
scripts/           冒烟测试和界面预览
examples/          配置示例
docs/              使用手册、代码导读
```

### 21.5 代码阅读顺序

建议：

1. `cli.py`：程序怎么启动；
2. `config.py`：配置和 Key 怎么合并；
3. `agent.py`：一轮对话怎么走；
4. `providers/`：消息怎么发给模型；
5. `tools/`：工具怎么执行；
6. `permissions.py`：什么时候询问；
7. `session.py`：怎么保存；
8. `checkpoints.py`：改文件怎么留底、怎么回退；
9. `tasks.py` + `tools/orchestration.py`：任务图怎么被调度；
10. `ui/`：界面怎么渲染。

更详细的逐文件说明见 `docs/代码导读.md`。
