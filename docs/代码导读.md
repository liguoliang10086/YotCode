# YotCode 代码导读（Python 小白版）

这份文档回答三个问题：**项目用了什么技术**、**每个文件是干什么的**、**从哪里开始看**。

---

## 一、这是什么项目？用了什么"脚手架"？

**先说结论：这个项目不是用某种脚手架工具生成的，而是纯手写的现代 Python 项目。**

你熟悉的"脚手架"可能是 Vue CLI、create-react-app 那种一键生成目录的工具。Python 世界更常见的是：
- **Django / Flask / FastAPI**：Web 框架脚手架（本项目没用，因为不是网站）
- **Poetry / uv / Hatch**：项目管理工具（本项目也没用）

本项目只用一个 **`pyproject.toml`**（Python 官方的项目配置文件标准，叫 PEP 621）声明依赖和入口，然后开发者自己创建了 `yotcode/` 目录结构。所以你要学的"框架"其实只有下面这几个库：

### 核心依赖（就 3 个）

| 库 | 是什么 | 本项目拿它做什么 |
|---|---|---|
| `textual` | 终端 UI 框架。可以把命令行窗口变成类似网页的交互界面，有按钮、面板、快捷键、鼠标点击 | 画整个聊天界面（`ui/` 目录） |
| `rich` | 终端美化库。让命令行输出彩色文字、Markdown、表格、代码高亮、diff 对比 | 渲染消息、工具卡片、错误提示 |
| `httpx` | HTTP 客户端。类似浏览器，可以发网络请求，支持异步和流式响应 | 调用大模型 API、抓取网页 |

### 只用于测试的依赖

| 库 | 是什么 |
|---|---|
| `pytest` | Python 最主流的测试框架 |
| `pytest-asyncio` | 让 pytest 能测试 `async` 异步函数 |

### 其余全是 Python 自带的标准库

`argparse`（解析命令行参数）、`asyncio`（异步并发）、`json`（处理 JSON 数据）、`dataclasses`（快速定义数据类）、`pathlib`（处理文件路径）、`subprocess`（启动外部程序，比如执行 Bash 命令）、`re`（正则表达式）、`abc`（定义抽象基类）等等。**不需要额外安装**。

### Python 版本要求

`pyproject.toml` 里写的是 `requires-python = ">=3.10"`，意思是至少要 Python 3.10。你电脑上是 3.14，完全没问题。代码里用了不少 3.10+ 的新语法（下文会解释）。

## 二、看代码前必须知道的 6 个 Python 概念

你是小白，先花 5 分钟了解这几个概念，后面读代码会顺畅很多：

### 1. `async def` / `await` —— 异步函数

普通函数是一步一步执行的；异步函数遇到 `await` 会"让出"控制权，让程序在等待网络响应时去干别的事（比如刷新界面）。调用异步函数必须用 `await`，否则它不会真正执行。

```python
async def run(...):        # 异步函数
    result = await agent.run(...)   # 等待另一个异步函数完成
```

本项目从头到尾都是异步的，因为要一边等大模型慢慢吐字，一边保持界面能响应你的按键。

### 2. `@dataclass` —— 自动帮你写 `__init__` 的装饰器

```python
@dataclass
class ToolResult:
    content: str
    is_error: bool = False
```

等价于手写 `def __init__(self, content, is_error=False): self.content = content ...`。省大量样板代码。你会在每个文件里看到它。

### 3. 类型注解 `str | list[Any]` —— 只是提示，不影响运行

`str | list[Any]` 意思是"这里可以是字符串，也可以是列表"。`list[str]` 是"字符串列表"。这些是写给人和编辑器看的，Python 运行时不检查。文件开头的 `from __future__ import annotations` 是为了让这些写法在旧版本也能用。

### 4. `ABC` + `@abstractmethod` —— 定义"接口规范"

`class Tool(ABC)` 表示"工具"的抽象基类，里面 `async def run(...)` 标了 `@abstractmethod`，意思是你不能直接创建 Tool，必须写一个子类实现 `run()` 方法才能用。这保证了所有工具都有统一的调用方式。

### 5. `async generator` / `yield` —— 边生成边返回

普通函数 `return` 一次性返回结果；带 `yield` 的函数每次产出一个值，调用方可以用 `async for` 一个一个接收。大模型逐字返回内容就靠它：

```python
async for event in provider.stream(...):   # 每收到一小段就处理一小段
    ...
```

### 6. 包（package）和模块（module）

`yotcode/` 目录下有 `__init__.py`，所以它是一个"包"。`from .agent import Agent` 里的点号 `.` 表示"当前包内"，`from ..types import Message` 的两个点表示"上一级包"。`__init__.py` 还定义了对外的版本号。

## 三、程序入口在哪里？

记住这条链：

```
你双击运行
   │
   ▼
run.cmd                          ← Windows 启动脚本（你已经有）
   │  优先用 .venv\Scripts\yotcode.exe
   │  否则 python -m yotcode
   ▼
yotcode/cli.py  →  main()       ← 真正的主入口（第 367 行）
   │
   ├─ 判断是不是无头模式（-p 参数 / 管道输入）
   │
   ├─ 无头模式  →  run_headless() →  Agent.run()
   │
   └─ 交互模式  →  ui/app.py 的 YotCodeApp.run()  →  Agent.run()
                                                      │
                                                      ▼
                                            ★ agent.py 第 364 行
                                              真正的主循环在这里
```

**一句话总结**：`run.cmd` 启动 → `cli.py:main()` 分发 → 无论哪种模式，最终都跑到 `agent.py` 的 `run()` 方法里那个 `for turn in range(max_turns)` 循环。

### 两种运行模式

| 模式 | 怎么触发 | 特点 |
|---|---|---|
| 交互 TUI | 直接运行 `run.cmd` | 全屏终端界面，能持续对话、点按钮、按快捷键 |
| 无头模式 | `yot -p "问题"` 或把内容通过管道传入 | 打印结果就退出，适合脚本和 CI 自动化 |

## 五、核心机制图解

### 1. Agent 主循环（最重要！）

大模型本身只能"说话"，不能真的读写文件。`agent.py` 做的就是不断重复下面的循环：

```
用户输入："帮我看看这个项目"
        │
        ▼
[第 N 轮] 把全部历史消息发给大模型（流式请求）
        │
        ▼
大模型返回内容，可能包含两类东西：
   ├─ 文字  ──────────────────────────► 显示在界面上
   └─ 工具调用（比如 Read(file_path="a.py")）
              │
              ▼
       先检查权限（要不要问用户？）
              │
              ▼
       执行工具，拿到结果（比如文件内容）
              │
              ▼
       把结果作为一条"用户消息"塞回历史
              │
              ▼
       回到第 N+1 轮，让大模型根据结果继续说
       
循环直到：模型不再请求工具 / 达到 max_turns / 用户按 Esc 打断
```

这段逻辑在 `agent.py` 的 `run()` 方法，第 **364** 行开始。强烈建议你先读这个方法开头的中文注释。

### 2. 工具系统

18 个工具都遵守同一个"接口"（`tools/base.py` 里的 `Tool` 类）：
- `name` / `description` / `input_schema`：告诉大模型"我有什么工具、参数怎么传"
- `run(data, ctx)`：真正干活的异步方法，每个工具自己实现
- `requires_permission` / `read_only` / `dangerous`：给权限系统看的标记
- `parallel_safe`：告诉 Agent 这个工具能不能和别的工具**并发**跑
- `touched_paths(data, ctx)`：告诉 Agent"这次调用会改哪些文件"，用来在改之前留检查点

`tools/__init__.py` 的 `create_tools()` 把它们组装成列表，`agent.py` 收到工具调用后按名字查表执行。

### 2.1 工具并发执行（`asyncio.gather`）

模型一轮里经常同时要求几个互不相关的操作（一次读 5 个文件、同时派 3 个子代理）。
`agent.py` 的 `_execute_tool_batch()` 按下面的规则处理：

```
遇到 parallel_safe 的工具  →  先攒着（batch）
遇到有副作用的工具          →  先把攒着的并发跑完，再执行自己（保证顺序）
本轮结束                    →  把攒着的并发跑完
```

并发用 `asyncio.gather` 实现，它**保证返回值顺序和传入顺序一致**，所以回填给模型的
`tool_result` 顺序永远和模型请求的顺序一致（Anthropic 协议要求两者一一对应）。

标了 `parallel_safe = True` 的工具：`Read` / `LS` / `Glob` / `Grep` / `BashOutput` /
`Skill` / `Task` / `TaskPlan`。判断标准是"不改共享状态 + 不需要弹权限窗"。

两个配套细节：

- **权限弹窗锁**：`_permission_lock` 是 `asyncio.Lock`，把"问用户"这一步串行化，
  否则多个并发工具会同时 `push_screen_wait` 把界面搞乱。父子 Agent 共用同一把锁，
  所以子代理和主代理也不会同时弹窗。
- **SSE 捕获改成 ContextVar**：`providers/base.py` 里原本用普通实例属性存"这次请求抓到的
  SSE 原文"，并发时会互相覆盖。改成 `ContextVar` 后每个任务各有一份，互不干扰。

### 3. 权限系统

每次工具调用前，`agent.py` 都会问 `permissions.py`："这个操作要放行吗？" 判断顺序大致是：

```
deny 名单（明确禁止）        → 拒绝
bypassPermissions 模式       → 全部放行
plan 模式 + 写操作           → 拒绝
ask 名单                     → 弹窗问用户
allow 名单                   → 放行
工具自己声明不需要权限       → 放行
acceptEdits 模式 + 项目内编辑 → 放行
其他                         → 弹窗问用户
```

### 4. 会话持久化

`session.py` 把每轮消息追加写到 `~/.yotcode/projects/<项目名>/<会话ID>.jsonl`，一行一条 JSON。所以关闭程序后用 `run.cmd --continue` 还能接着聊。

### 5. Skill 技能包：渐进式披露

`skills.py` 扫描 `.yotcode/skills/*/SKILL.md`（以及 `.claude/skills/`、用户级目录），
每个技能包就是一个带 frontmatter 的 markdown 文件。

关键设计是**只往系统提示词里放名字和描述**：

```
prompts.py: build_system_prompt()
  └─ skill_listing(cwd, home)
       └─ load_skills()      只读 frontmatter，不读正文
       └─ 输出 "- name: description"  ← 只有这些进提示词
```

真正需要时，模型调用 `Skill` 工具（`tools/skill_tools.py`），它才去读正文：

```
Skill 工具 → skill_body(spec) → 读 SKILL.md → 展开 @相对路径 导入 → 返回给模型
```

好处是：几百个技能包也只占几十 token；无关的技能永远不会污染上下文。
这和 `CLAUDE.md` 的做法相反 —— 记忆文件是**无条件全量**塞进提示词的。

`@相对路径` 导入复用了 `memory.py` 的 `expand_imports()`，两边语法一致。

### 6. 检查点：改文件之前先留个底

`checkpoints.py` 负责存快照，触发点在 `agent.py` 的 `_execute_tool()`：

```python
# 改文件之前先留个检查点，AI 改坏了还能用 /revert 退回去。
self._snapshot_before_change(tool, block.input)
result = await tool.run(block.input, self.ctx)
```

"这次调用会改哪些文件"由**工具自己声明** —— 这就是 `Tool.touched_paths()` 这个扩展点。
`Write` / `Edit` / `MultiEdit` 各自实现它并返回目标文件路径；其他工具返回空列表（意思是"不知道"，那就不快照）。

存储布局：

```text
.yotcode/checkpoints/<会话ID>/<检查点ID>/
    meta.json      元信息（时间、哪个工具改的、涉及哪些文件）
    blobs/0.txt    每个文件改之前的内容
```

按会话分目录，所以只能回退"这次会话改的东西"，不会误伤你之前的工作。

恢复语义看着简单，但很关键：

- 改之前**就存在** → 把旧内容写回去；
- 改之前**不存在**（这次新建的）→ 直接删掉。

整个快照过程包在 `try/except` 里 —— 存快照失败绝不能拖垮主流程。

### 7. 任务编排：代码真的在调度，不只是"记下来"

`tasks.py` 定义任务图（`TaskNode` + `depends_on` 依赖边），`tools/orchestration.py` 负责执行。

核心是 `run_graph()` 这个循环：

```python
while graph.pending_count() > 0:
    ready = graph.ready()          # 依赖全部完成、且还没跑过的任务
    if not ready:
        graph.mark_unreachable()   # 上游挂了 → 下游标记为"跳过"
        break
    batch = ready[:max_parallel]
    outcomes = await asyncio.gather(*(run_one_task(n, graph, agent) for n in batch))
```

每一轮挑出"依赖已满足"的任务**并发**跑。`run_one_task()` 内部是重试循环：失败就再来一次
（默认 2 次，最多 5 次），用完次数才标记 `FAILED`。

上游结果怎么传给下游？`build_prompt()` 在拼提示词时，把已完成的上游任务报告追加进去：

```python
parts.append("以下是已经完成的上游任务结果，请基于它们继续：\n\n" + upstream_reports)
```

每个任务由一个**子代理**执行（`agent.run_subagent(..., raise_on_error=True)`），所以子代理之间
上下文互相隔离，主对话不会被一堆中间过程污染；`raise_on_error=True` 让调度器能真正感知成败。

环检测用 DFS 三色标记法（0=未访问 / 1=在当前路径上 / 2=已完成），发现环直接报错，不会死循环。

### 8. 界面和 Agent 怎么通信

`ui/app.py` 里的 `UICallbacks` 是一个"桥"：Agent 每次产生文字、开始工具、收到结果、请求权限，都会调用回调，回调再把消息转给界面更新。反过来，你按回车发送内容，界面调用 `agent.run()`。两边互不依赖。

界面本身采用“深色终端（Deep Terminal）”风格：`#0b0b0e` 背景、`#d97757` 陶土橙强调色、`#212128` 分隔线；对话左侧有一条极淡的时间线，工具调用压成 `└ Name arg  ✓ 0.4s` 一行，输出用 `⎿` 前缀；只有编辑文件才显示带边框的 diff 卡片。输入框是圆角容器，左侧 `❯`、右侧 `⏎` 发送；底部状态栏显示权限模式、token、费用和上下文占用条。配色和尺寸集中在 `ui/render.py` 的 token 与 `ui/theme.tcss`。

#### 回车为什么能可靠发送

`PromptTextArea` 是 `TextArea` 的子类。Textual 会把 TextArea 包在一个内部的 `Horizontal` 里，所以它的 `self.parent` 不是 `PromptArea`。早期代码用 `self.parent` 找发送逻辑，导致回车拿不到正确对象。现在创建输入框时会显式传入 `owner`（也就是 `PromptArea`），回车时直接调用 `owner.submit()`。

另外，Textual 的 `TextArea._on_key` 是 `async` 方法，子类覆盖后必须 `await` 基类实现，否则光标、选区等默认行为会丢失。当前实现是：

- `Enter`：提交；
- `Shift+Enter` / `Ctrl+J`：插入换行；
- `Tab`：有补全时接受补全，没有补全时不把焦点移走；
- `↑` / `↓`：在补全列表或历史消息之间移动。

## 八、如何查看"发给大模型 / 大模型返回"的完整日志（调试利器）

程序**默认开启** API 交互日志，每次启动会把旧日志清空重写。文件位置：

```
项目根目录/.yotcode/api-log.txt
```

里面按调用顺序记录了每一轮：

- **REQUEST 部分**：完整的 system 提示词、所有 messages（含工具执行结果回填）、工具清单和参数——也就是"你发给大模型的一切"
- **RESPONSE 部分**：thinking 思考过程、正文回答、工具调用请求，以及每个流式事件的时间点和内容——也就是"大模型返回的一切"
- 每次调用的模型名、耗时、错误（如果失败）

这样你就能验证之前困扰你的问题：比如请求里到底有没有要求思考、上游有没有返回 `reasoning_content`、为什么慢（看每个事件的时间间隔）。

**开关方式**（在 `run.cmd` 前用 `set` 设置环境变量）：

```bat
set YOTCODE_API_LOG=0                      :: 关闭日志
set YOTCODE_API_LOG=D:\logs\my-log.txt     :: 自定义日志位置
run.cmd
```

日志实现位于 `yotcode/apilog.py`，接入点在 `yotcode/providers/base.py` 的 `stream()` 方法——因为所有供应商都经过这个方法，一处接入全覆盖。

### 想看"原汁原味的 HTTP 报文"？

程序还会同时生成一份**网络层真实报文**日志：

```
项目根目录/.yotcode/api-http.txt
```

它用 httpx 的 event_hooks 在网络层拦截，记录的是实际发出去的 HTTP 请求和收到的响应：

- **请求**：`POST 完整URL` 请求行、全部请求头（API Key 已脱敏显示成 `sk-a...xyz  <已脱敏>`）、**实际发送的 JSON 请求体**（就是发给大模型的字节，美化后显示）
- **响应**：`HTTP/1.1 200 OK` 状态行、全部响应头、**响应体原文**（SSE 流式就逐条列出 `data:` 内容）

注意：`--mock` 离线模式不发真实 HTTP，所以这份日志在 mock 下是空的；用真实模型（`run.cmd`）跑一次就有完整报文。两份日志用同一个开关 `YOTCODE_API_LOG` 控制。

实现位于 `yotcode/httplog.py`，通过 `Provider` 构造时的 httpx `event_hooks` 自动接入，对 Anthropic 和所有 OpenAI 兼容供应商都生效。
